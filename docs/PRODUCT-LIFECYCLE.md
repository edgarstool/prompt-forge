# Prompt Forge 產品流程

這份文件讓不熟悉產品開發的人，也能看懂一個產品如何從想法走到可交付版本。

## 全貌

```text
問題發現
→ 產品定義
→ 使用情境
→ 範圍切割
→ 原型
→ 驗證
→ 實作
→ 測試
→ 發布
→ 觀察與改良
```

這不是只能往前走的流水線。任何階段發現方向錯了，都可以回頭修正。產品不是考卷，比較像反覆鍛打的金屬。

## 1. 問題發現

先回答：使用者真正卡在哪裡？

Prompt Forge 的初始問題是：

- 使用者知道自己想做什麼，但不一定知道如何寫成高品質 Prompt。
- 不同 Agent 擅長不同任務，使用者常要自己判斷該交給誰。
- 技術型 Prompt 容易引用過時 API 或文件。
- 一般 Prompt 產生器常提供漂亮文字，卻缺少驗收與交付條件。

**本階段交付物：** Problem Statement（問題陳述）。

## 2. 產品定義

把問題變成一句清楚的產品承諾：

> 使用者描述目標後，Prompt Forge 產出一份適合指定 Agent、可直接執行、內建驗收的 Prompt。

**本階段交付物：** README、產品原則、Non-goals。

## 3. 使用情境

不要先幻想所有功能，先挑真實場景：

1. 幫我整理一個資料夾。
2. 幫我研究免費 VM 與 credits。
3. 幫我修一個 GitHub repo。
4. 幫我設計 Cloudflare / MCP 工作流。

每個情境都要有：

- 原始輸入
- 預期路由
- 預期 Prompt
- 成功判斷

**本階段交付物：** examples 與 tests。

## 4. 範圍切割

第一版只做能證明價值的最小閉環：

```text
需求
→ 分類
→ 選 Agent / 工具
→ 組 Prompt
→ 評估品質
→ 輸出
```

第一版不做登入、計費、市集或複雜 UI。

**本階段交付物：** v0.1 Scope。

## 5. 原型

原型的目的不是漂亮，而是快速驗證：

- 路由規則是否合理？
- 產出的 Prompt 是否真的能執行？
- Context7 是否只在需要時加入？
- 輸出是否太長或太像教學？

第一個原型可以是純文字規格、JSON Schema 或 CLI，不必先做網站。

**本階段交付物：** Prompt schema、router rules、範例輸出。

## 6. 驗證

把模糊感覺改成可判斷條件。

Prompt Forge v0.1 的基本驗收：

- 可以直接複製使用。
- 沒有把能合理推斷的細節全部問回使用者。
- 包含清楚目標、範圍、驗收與停止條件。
- 技術任務會要求查版本相符的官方文件。
- 不會把低風險工作包成龐大安全儀式。

**本階段交付物：** evaluator 與 test cases。

## 7. 實作

驗證規格後才開始寫真正的 router、composer、adapter 與 evaluator。

實作原則：

- branch 隔離
- 小量依賴
- 每個模組能單獨測試
- 規則與模型輸出分開
- 不把 secret 寫進 repo

**本階段交付物：** 可執行程式與測試。

## 8. 測試

至少包含：

- 單元測試：單一規則是否正確。
- 情境測試：完整輸入是否得到預期輸出。
- 回歸測試：修正一處後，舊案例是否仍通過。
- 人類試跑：實際把 Prompt 交給 Agent。

**本階段交付物：** 測試報告。

## 9. 發布

第一個可用版本不等於完成品。

發布時要交代：

- 版本做得到什麼
- 做不到什麼
- 如何使用
- 已知問題
- 如何回報失敗案例

**本階段交付物：** Release notes、tag、使用說明。

## 10. 觀察與改良

真正的產品學習從使用後開始。

我們會記錄：

- 哪些 Prompt 被直接採用
- 哪些被大量修改
- 哪些 Agent 路由判錯
- 哪些問題其實不該交給 LLM
- 哪些規則讓輸出變得太長

失敗案例不是黑歷史，而是測試資料礦脈。
