# Prompt Forge v0.1 Specification

## 目標

把一句模糊需求轉換成一份可直接交給合適 Agent / tool 執行、可驗收、可停止、可回傳 evidence 的 Prompt / task contract。

Prompt Forge 是 **EDGAR PromptOS 的 executable compiler / factory**。PromptOS 是治理／任務契約架構；Prompt Forge 只負責其中可執行的 compile / evaluate 子系統。

架構邊界詳見 [`PROMPTOS-ARCHITECTURE.md`](PROMPTOS-ARCHITECTURE.md)。

## v0.1 核心流程

```text
User Request
→ Intent Classification
→ Authority / Evidence / Constraint Resolution
→ Risk & Permission Check
→ Agent / Tool Routing
→ Context Policy
→ Assumption / Unknown Handling
→ Prompt Composition
→ Prompt Evaluation
→ Final Task Contract
```

目前 local implementation 的 deterministic loop 為：

```text
intent → risk → route → context policy → compose → evaluate
```

Execution orchestration、long-running workflow、evidence collection 與 durable state write-back 屬更大的 EDGAR-OS / Agent Platform integration，不是 v0.1 local compiler 的完成前置條件。

## 輸入

v0.1 至少接受：

```json
{
  "request": "幫我把這個 repo 整理好",
  "preferred_agent": null,
  "known_context": [],
  "constraints": []
}
```

只有 `request` 必填。其餘資訊缺少時，系統應合理推斷或標示假設，不應預設全部問回使用者。

系統不得把未驗證推論包裝成 Known Fact。能以 live / primary evidence 補足而且成本合理時，優先查核；否則保留為 explicit assumption / unknown。

## 任務類型

第一版支援六類：

1. `research`
2. `coding`
3. `local-files`
4. `cloud-saas`
5. `agent-workflow`
6. `deterministic-tool`

`deterministic-tool` 代表更適合 PowerShell、Python、parser、regex、diff 或其他確定性工具的工作。

## 路由輸出

```json
{
  "task_type": "coding",
  "recommended_agent": "codex",
  "supporting_tools": ["github", "context7"],
  "confidence": 0.86,
  "assumptions": [
    "repository is already available to the selected agent"
  ]
}
```

路由層應能區分：

- human goal / intent
- authority / permission
- known evidence
- constraints
- assumptions / unknowns
- recommended executor / tool

這些不是同一種資訊，不應用單一 priority 把它們互相覆蓋。

## Context / Freshness Policy

符合下列任一條件時，Prompt 應加入 Context7 或等效 primary / official source 查核：

- 涉及 library、framework、SDK、API、CLI。
- 涉及可能快速更新的 cloud service。
- 使用者要求特定版本。
- Agent 需要產生版本敏感的 code 或設定。

不應為純寫作、一般整理、固定檔案操作或不涉及外部 API 的任務硬塞 live documentation。

Freshness 是任務條件，不是儀式。只有會實質影響正確性的資訊才要求 live verification。

## Prompt / Task Contract 組成

最終輸出可依任務縮放，但應能表達：

- Goal
- Known Facts / Evidence
- Authority
- Scope
- Constraints / Permissions
- Assumptions / Unknowns
- Selected Executor / Tools
- Context Freshness Requirements
- Execution Task
- Validation / Acceptance Criteria
- Deliverables
- Stop Conditions
- Evidence to Return
- State Transition / Write-back Target

不是每個簡單任務都要把全部欄位寫成大段文字；欄位可以合併或省略，但不可讓重要邊界消失。

風險較高或 repo 施工任務，再加入：

- Branch / Worktree Isolation
- Rollback
- Forbidden Actions
- High-risk confirmation gate

## 追問規則

只有以下情況才追問：

- 缺少資訊會導致完全不同的成果。
- 涉及 secret、付款、production、重大權限或不可逆資料。
- 無法識別目標檔案、repo 或外部服務，且工具／來源不能自行解析。
- 使用者明確要求先討論再執行。

其餘情況採用合理、可逆假設並在 Prompt 中明示。

## Evidence Return / State Transition

PromptOS 的完整 lifecycle 不以「模型回答了」為完成。

執行 handoff 應在適當任務中要求回傳：

- 做了什麼
- 驗證結果
- 變更位置
- branch / commit / PR（若有）
- 未完成 / blocker
- 使用過的 live evidence
- canonical state 是否已更新

若任務涉及跨 session 續接，重要 state transition 應寫回對應 canonical SSoT / Worklog / project system，而不是只留在聊天紀錄。

## 評估標準

每份 Prompt 以 0 或 1 評分：

| Check | Pass condition |
|---|---|
| Executable | 能直接交給 Agent / tool |
| Goal clarity | 成果明確 |
| Scope clarity | 有包含與不包含範圍 |
| Validation | 有成功判斷 |
| Deliverables | 有回報內容 |
| Stop conditions | 知道何時停下 |
| Assumption discipline | 合理推斷且有揭露 |
| Context freshness | 需要時加入最新文件查核 |
| Proportional safety | 保護措施與風險相稱 |
| Concision | 沒有不必要的前提堆疊 |

v0.1 合格門檻：至少 8 / 10，且 `Executable`、`Goal clarity`、`Validation` 必須通過。

## 第一批測試案例

### Case A：本機資料夾整理

輸入：

> 幫我把這個資料夾整理好。

預期：路由到 local-files；先盤點、分類、保留原檔、產出報告，不大量追問。

### Case B：免費 VM 研究

輸入：

> 幫我找現在還能用的免費 VM 和 credits。

預期：路由到 research；要求即時搜尋、來源日期、限制與比較。

### Case C：GitHub repo 修復

輸入：

> 幫我修好這個 repo，測試完開 PR。

預期：路由到 coding；使用 branch；需要時接 Context7；跑測試、開 PR、回報 commit / validation / unresolved items。

### Case D：Secret 清單整理

輸入：

> 幫我把這些 secret 整理成可匯入清單。

預期：判斷是否應由 deterministic tool 處理；不把 secret 值送去不必要的外部模型；輸出 schema 與驗證方式。

## v0.1 完成定義

- 有可讀的 router 規則。
- 有可組合的 Prompt template。
- 有 Context / freshness policy。
- 有 evaluator。
- 四個測試案例能產出合格 Prompt。
- 有一個最小可執行入口，CLI 或測試 runner 皆可。
